## 看板娘

用的是 <https://github.com/stevenjoezhang/live2d-widget>（npm 包名是复数 `live2d-widgets`）。它自 1.0 起不再需要后端 API，模型清单写在 `source/live2d/waifu-tips.json` 的 `models` 字段里，我指到 `/asset/live2d/umaru/model.json`。渲染核心是仓库自带的 `dist/live2d.min.js`，即 Live2D Cubism 2 Web SDK，所以 umaru 这种 `.moc` 老模型可以直接用。模型本身来自 <https://github.com/HesperusVenus/live2d>，那是个仓库根没有 LICENSE 的个人合集，用的是 pio 那套 `live2d_model.json` 字段（`hit_areas`、`expressions`、`sound`），widget 一样能读；这个授权缺口记在模型目录的 `SOURCE.txt` 里。

想换模型：往 `themes/mustom/source/asset/live2d/` 放一个新模型目录，再在 `waifu-tips.json` 的 `models` 里加一条，`paths` 指向它的 model json；`loader.js` 的 `tools` 数组控制右下角按钮（`hitokoto` 一言、`photo` 拍照、`info` 介绍、`quit` 关闭）。

## ShiftNav

ShiftNav 是 WordPress 插件，前端本身只是「一份 CSS + 一个 jQuery 插件 + 一段 off-canvas DOM」，所以移植不需要 WordPress：

1. `jquery.min.js` → `shiftnav.min.js`（原样取自插件 SVN trunk）
2. `shiftnav_data` 这个全局对象原本是 WP 用 `wp_localize_script` 注入的，我在胶水脚本里手工补齐了它读取的 16 个键
3. 抽屉 DOM 照 vcb-s 线上渲染结果的结构搭：`.shiftnav[data-shiftnav-id] > .shiftnav-inner > nav.shiftnav-nav > ul.shiftnav-menu`，开关按钮 `#shiftnav-toggle-main.shiftnav-toggle[data-shiftnav-target]`
4. 菜单项从主题渲染好的 `.p-menus .p-menu` 里读；主题是用 JS 异步填充这块 DOM 的，所以胶水脚本每 250ms 轮询一次，拿到内容就停
5. `shift_body` 留空，即不做「推挤主体」的位移，抽屉直接盖在上面——主题的布局有自己的 fixed 头部，推 body 会错位
6. 断点 991px：宽屏隐藏 ShiftNav 开关、用主题自带抽屉；窄屏反过来，并给 `.m-header` 让出左上角的位置

## 加载界面

主题启动时叠了三层：`.m-launch` 是整屏 `--color-link` 红底，`.m-spinner` 是整屏 `#ffffffee` 白纱加一个转环，`.m-progress` 是顶部进度条。前两层太刺眼，做法是：

- `.m-launch` 直接 `display: none`
- `.m-spinner` 只删 `background`，转环动画和 `.active` 期间的 `pointer-events: all` 都留着，进度条不动

DOM 节点本身一个都不能删。`main.js` 的启动清单是靠这些节点计数决定"加载完了没有"，少一个节点 `activateSpinner(false)` 就永远不执行，页面卡在加载态。

## Markdown 配置

`_config.yml` 里写了一段显式 `markdown:`，值就是 hexo-renderer-markdown-it 7.1.1 当前的默认值，所以它对产物是逐字节的 no-op——这点是构建前后对 `public/api/posts/*.json` 取 md5 比出来的（比对时要排除 `api/site.json`，它内嵌 `swPath: /sw.js?t=<构建毫秒>`，每次必变）。写死它的唯一目的是钉住渲染行为，将来升级 renderer 时排版不会静默变化。

## 直播间页

front-matter 是 `layout: page` + `name: live` + `parts: [page]`。三个约束值得记：

1. `parts` 里只能写主题认识的名字。`main.js` 只对 `page` 这个 part 做初始化，写一个不存在的 part 会让启动清单凑不齐，和删 DOM 节点同一个死法。
2. 正文里的 `<script>` 由 `part/page.js` 重新执行——它照抄一个新建的 script 元素再插进文档，**原来的 id 会丢**。所以页内脚本的全局数据必须写在脚本第一行，不能靠 `getElementById` 去捞一个带 id 的 script 标签。
3. markdown-it 把 `<style>` / `<script>` 当 HTML block type 7，里面**不能有空行**，有空行就会被截断。

线路表 `routes` 支持三种形态：字符串是直连媒体地址（m3u8 走 hls.js、mp4 走原生 `canPlayType` 判断），带 `embed` 的对象是第三方播放器的 iframe，带 `room` 的对象是 B 站直播间的跳板卡片。点赞数只写 `localStorage`，没有服务端计数。

## B 站直播嵌不进来的部分，和唯一能嵌的那个

| 端点 | 实测结果 |
| --- | --- |
| `www.bilibili.com/blackboard/live/live-activity-h5-player.html?roomid=…&type=room` | 200，**没有任何 X-Frame-Options / CSP**，可嵌；自带 `bilibili-lmp-danmaku` 弹幕层；未开播时显示房间封面＋播放按钮 |

所以：弹幕是"有"的，但只有借 B 站自己的播放器才有。想自己写代码读弹幕、自己取流，静态托管上做不了，得有个后端做中转（把带 Origin 的请求换成不带的服务端请求，再把 FLV 和弹幕转发出来）。

## 加一个菜单项要改三处

`themes/mustom/_config.yml` 的 `menus.main.<key>`、`asset/lang/zh-cn.yml` 的 `menus.main.items.<key>`、以及同文件的 `pather.<key>`。少最后一项，页面顶部面包屑就打印 `undefined`。英文那份 `en.yml` 同理两份都要加。

## 换壁纸和半透明面板

颜色全在 `themes/mustom/source/asset/css/_common/color.styl`，是一份份 CSS 自定义属性，按皮肤分四块：`:root`（默认）、`:root.gray`、`:root.colorful`、`:root.night`。切皮肤只是给 `<html>` 加减 class（`asset/js/part/skin.js` 的 `set()`），所以改之前要先确定改的是哪一块——不带 class 的那块才是打开页面看到的。

背景图不是单独写 `background-image`，而是塞进 `--color-body-back`。`layout.styl` 里 body 已经带了 `background-repeat:no-repeat; background-size:cover; background-attachment:fixed`，所以只要这个变量的值是 `url(...)`，整站就是一张固定铺满的壁纸。图放在 `themes/mustom/source/asset/img/bg.jpg`，路径由 `dimension.styl` 的 `$picurl` 给出。原版只有 `:root.colorful` 的 body 背景用这个变量，它指向 `https://source.unsplash.com/1920x1080/?wallpaper`，实测现在请求只拿到 `503` 加一个 heroku 的 "Application Error" 页，取不到图，也就是说 colorful 那套皮肤的"随机壁纸"一直是加载失败的——换成本地图之后这块顺带修好了。

"透明"就是在十六进制色后面拼两个字母的 alpha。先按 70% 透明做的（后缀 `4d`，`0x4d / 0xff ≈ 30%` 不透明），改的背景类变量是这些：`--color-background`、`--color-clear`、`--color-header-background`、`--color-progress-back`、`--color-menus-hover`、`--color-extension-back`、`--color-extension-hover`、`--color-recentposts-more-back`、`--color-iconlib-iframe-back`、`--color-settings-switch-off`。没动的两类：`--color-menus-active-background` 和 `--color-toc-active-background` 是选中项的深底白字，透明了字就压在照片上；`night` 那套整体保持不透明。

`4d` 实测下来正文区（好几层白叠出来）还能读，但引用块、灰色小字这类本来就浅的文字压在照片亮部会糊，所以定稿换成 `b3`（70% 不透明 = 30% 透明）。以后要调就改这一处后缀，想保住通透感也可以留着 `4d` 再给面板加 `backdrop-filter: blur(...)`。

图本身是 pixiv 作品 67481841（画师 lemontea），来源地址记在 `dimension.styl` 的那行注释里。pixiv 上的作品默认不含任何再发布授权，这条只是把出处留在仓库里，不构成授权。

## 一言面板的换行，和作者行那块底色

句子容器是 `.p-hitokoto-word`（`asset/css/_part/hitokoto.styl`），原版没写 `word-break`，而中文排版允许在任意两个汉字之间断行，所以句子一超过一行就被腰斩——"离离原上草，一岁一枯／荣。"这种。改成 `word-break: keep-all` 之后，CJK 之间的断行机会全部取消，只剩下标点后那些，实测（420px 宽、24px 字）：

```
君不见，黄河之水天上来，
奔流到海不复回。君不见，
高堂明镜悲白发，朝如青丝暮成雪。
```

三行都收在 `，` 或 `。` 上，没有一行是从词中间断的。真实面板里把 `.p-hitokoto-word` 压到 300px 复测也是同样：`小荷才露尖尖角，` / `早有蜻蜓立上头。`。

`keep-all` 有个必须配兜底的副作用：整句不带标点时就一个断点都没有，文字直接撑破容器横向溢出（实测 32 字无标点句 `scrollWidth` 744 > `clientWidth` 420，而 `.p-hitokoto` 是 `overflow: hidden`，等于把后半句裁掉）。所以同一块补了 `overflow-wrap: break-word`——它只在"这一行无论如何放不下"时才强制断，同一句 32 字变成 17+14 两行，正常句子仍然只在标点处断。这套是纯 CSS，逐字打字的动画（`asset/js/part/hitokoto.js` 每 160ms 改一次 `innerText`）不用动，重排自然跟着走。

作者行 `.p-hitokoto-from` 是 `position: absolute`，压在面板底部那张 pixiv 图上，图没有底色，字直接糊在画上，所以要一块和面板同款的底色。这块底色**不能**加在 `.p-hitokoto-from` 这个块上：块上有 `line-height: 6`，整块铺底会在图上盖出一条 6em 高的横带。可行的形态是把 `-「 `、名字、` 」-` 三段收进一个盒子——伪元素挂在行内的 `.p-hitokoto-name` 上，再给它 `background: var(--color-background)` 加 `display: inline-block`，这样一个盒子的宽度天然等于"装饰 + 名字 + 装饰"的总长，底色是一整块。用的变量和面板、句子同一个，所以跟着皮肤走（colorful 是 `#ffffffdd`、gray 是 `#ffffff`、night 是 `#000000cc`）。

为什么要收成单盒：先前那版把底色分别加在 `.p-hitokoto-from::before`、`.p-hitokoto-name`、`::after` 三个兄弟行内盒上，实测在名字和 `」-` 之间留了一道 **6.667px 完全没被涂到**的缝。症状是 `::after` 的 `content` 以空格开头（`' 」-'`）时那个空格不被绘制，背景从 `」` 才开始画；`-「 ` 和名字之间实测 0px，没缝（尾随空格被画了，前导没有——只复现到这一层，规范上为什么不对称没核，B 级）。常见的绕法是那个位置换成不换行空格 `\a0` 或改 `padding`，但那样装饰和名字之间的间距得重调，所以这里选了收单盒。改成单盒以后，量到的白框 rect 宽 114.2px，正好等于旧版三段的并集（27.1 + 60 + 6.667 + 20.43）；截图放大四倍逐列扫，框内没有一列掉回图片本身的亮度（框左外沿 123、右外沿 121，框内 236-238，只有字墨处才下陷到 188/109/51）。

顺带修了一个改之前就在的问题：`:root.night img { filter: brightness(0.8) }`（写在 `layout.styl` 末尾那一段夜间规则里）会让 `img` 变成层叠上下文，和 `.p-hitokoto-from` 落在同一层、DOM 序又在后面，于是夜间模式下作者行整条被图片盖住、根本看不见。给 `.p-hitokoto-from` 加 `z-index: 1` 后夜间才真正看得到那块底色。三种皮肤 + 480px 移动端各自截图核过。

| --- | --- | --- | --- |
| 眼睛 | `p-footer-pv` | 运行时 JSONP 请求 `//busuanzi.ibruce.info/busuanzi` 的 `site_pv`（`main.js` 里两处，启动时和每次 `pushState` 之后各一次） | 是，页面浏览量 |
| 人 | `p-footer-uv` | 同一份响应的 `site_uv` | 是，独立访客 |
| 文档 | `p-footer-wd` | `/api/site.json` 的 `word4site`，Hexo 构建时算出来的全站字数 | 不是 |

不蒜子（busuanzi，接口域名 `busuanzi.ibruce.info`）是一个免费的极简访问计数器：不用注册、不用后端，页面里放一段脚本，它按这次请求的 Referer 域名返回几个数，走的是 JSONP（所以也不需要对方允许跨域）。它拿不到任何访客身份，UV 只能按访客侧特征粗去重（圈内一般说法是 IP 加 UA，官方没公开算法），换网络、换浏览器、运营商复用出口 IP 都会算错，所以这四个数的定位是"图个乐的大致量级"，不是分析数据。

所以你看到的那个 `3.1k` 是"这个站一共多少字"，不是人数——往这篇里加完这几节再构建，它就变成了 `4k`，正好当场验证了这个数的性质。GitHub Pages 是纯静态托管，没有服务器记账，但不蒜子是按请求 Referer 的域名统计的第三方服务，所以 PV/UV 在 Pages 上照常能跑——`curl "https://busuanzi.ibruce.info/busuanzi?jsonpCallback=BusuanziCallback_999"` 实测回来的是 `try{BusuanziCallback_999({"site_uv":10,"page_pv":10,"version":2.4,"site_pv":10});}catch(e){}`。参数名必须是 `jsonpCallback`，写成 `callback` 会回 `Bad Request`。这类第三方计数的两个固有问题：被刷没有防护，服务哪天关了就永远停在最后一个值上（初始占位是 `∞`）。

文章页头部眼睛旁边那个数字是"本文阅读量"。原版它走 LeanCloud（`leancloud_visitors` 配 Valine 的 visitor 模式），而 [LeanCloud 官方公告](https://docs.leancloud.cn/sdk/announcements/sunset-announcement) 写的是：2026 年 1 月 12 日起停止新用户注册，2027 年 1 月 12 日正式停止服务，之后数据按合规要求清除。这条依赖不值得接，所以换成了同一个不蒜子的 `page_pv`。

不蒜子的响应里除了全站两个数，还带一个按请求 Referer 的 URL 记账的 `page_pv`，实测：

| Referer | 返回 |
| --- | --- |
| `https://takomitkm.github.io/` | `site_pv:11`、`page_pv:11` |
| `https://takomitkm.github.io/posts/2659281223/` | `site_pv:12`、`page_pv:1` |
| `https://takomitkm.github.io/posts/1406938971/` | `site_pv:13`、`page_pv:1` |

也就是说"这一页被打开过几次"本来就是现成的，不用再引第二个服务。填充点在 `main.js` 的两处不蒜子回调里（启动时一次、每次 `pushState` 之后一次），写进 `.p-post-pv-num`；`comment.js` 里原来那段给 `.leancloud_visitors` 设 id 和 `data-flag-title` 的代码删掉了。代价是三个数现在全押在同一家第三方上，它哪天停了整站统计一起回到 `∞`；真要换，方向是可自托管、带导出接口的 GoatCounter 一类，但那要先有账号和自己的域名。`Valine.min.js` 和 LeanCloud 的 `av-min.js`（合计约 268 KB）现在还在每页加载，只是评论本来就没开，要清随时能清。

### site_pv 和 site_uv 能清零吗：不能

这两个数是**域名维度的累计**，存在不蒜子自己的服务器上，统计键是你站点的 hostname，站方没有任何写入口。三条核过的证据：

| 检查 | 结果 |
| --- | --- |
| 官方文档 FAQ 第 5 条（`ibruce.info/2015-04-04/busuanzi/`） | 原文"我的网站已经运行一段时间了，想初始化访问次数怎么办？——请先注册登录，自行修改阅读次数。" |
| 不蒜子首页 `busuanzi.ibruce.info` 的登录/注册弹窗 | "不蒜子暂不开放注册，攻城狮们正在火热内测中，敬请期待。"（2026-09-28 实测）——FAQ 指的那条自服务入口需要账号，而注册从没开放过 |
| 客户端脚本 `busuanzi/2.3/busuanzi.pure.mini.js`（1939 字节，全文读过） | 请求参数只有一个 `?jsonpCallback=`，没有 reset / clear / modify 端点 |

网上"不蒜子 UV/PV 初始化 / 清零"的教程全部是**显示层加偏移**（在自己页面里给返回值再 +一个基数，用来给新站补历史），反向做不出清零，只会让显示数字和真实数字永久错开。所以这两个数保留原样显示，含义写在页脚气泡里，不做任何加工。

这个站的 `site_uv` 一度等于 `site_pv`，是因为我为了测接口用 curl 反复直连打请求——curl 没有浏览器特征，每次都被当成一个新访客。要真想让计数从零开始，唯一的杠杆是换统计键（不蒜子按 hostname 记账，换自定义域名后新域名从 1 开始），那是换域名，不是清零。

### 不蒜子一共能给什么

接口一次请求返回四个字段：`site_pv`、`site_uv`、`page_pv`、`version`（最后一个是服务自己的版本号，不是统计量）。三个统计量现在全站都用上了：

| 字段 | 统计键 | 显示位置 |
| --- | --- | --- |
| `site_pv` | 站点 hostname | 页脚眼睛 |
| `site_uv` | 站点 hostname | 页脚人 |
| `page_pv` | 请求 Referer 的完整 URL | 文章页头部眼睛；这一轮起独立页面（`/live/`、关于）的标题条右侧也显示 |

官方文档另外两条能力：一是**只计数不显示**（只引脚本不引标签）；二是明确写了**不做**列表页逐篇阅读量——"不蒜子为保持极简，暂不支持在站点文章摘要列表中（如首页）逐个显示每篇文章的阅读次数"，所以归档页每篇后面那个数拿不到，除非引第二个服务。

`page_pv` 是按 URL 记账的，所以同一个填充点（`main.js` 里那两处回调写 `.p-post-pv-num`）顺手也能喂独立页面——页面模板 `layout/_partial/_part/page.ejs` 的标题条右侧加了一个 `.p-page-pv`，元素沿用 `.p-post-pv-num` 这个 class，JS 一行没改。

## 页脚注释气泡

三个图标各包了一层 `.p-footer-count-item`，里面挂一个 `.p-footer-tip`，文案走主题的 i18n：`data-lang="footer.tipPv|tipUv|tipWd"`，中英两份在 `asset/lang/{zh-cn,en}.yml`。桌面靠 `:hover`/`:focus`，触屏靠 `main.js` 里给这些元素绑的 click 切 `.on`（点另一个会自动关掉前一个）。两个坑：`.p-footer` 自己是 `overflow:hidden`，所以气泡的定位上下文必须是整行 `.p-footer-count` 而不是单个图标，否则最左边那个会被裁掉一半；stylus 里 `&:hover, &:focus, &.on` 这种并列父选择器嵌子元素时会编译出一个光秃秃的 `.p-footer-tip`，把默认隐藏样式覆盖掉，得把三条选择器整行写全。

## 播放器

主题自带 APlayer + MetingJS（`asset/js/plugin/APlayer.min.js`、`Meting.min.js`），面板在 `layout/_partial/frame.ejs` 里无条件渲染，开关只有一个字段：`themes/mustom/_config.yml` 的 `meting.id`。判定在 `main.js` 里——

```js
const mj = el && el.querySelector('meting-js');
if (mj && mj.getAttribute('id')) _run_Meting();
else el && el.remove();
```

也就是说 id 给空字符串时整个 `.p-audioplayer` 面板会被删掉（原版作者的歌单 id 之前就是这么清掉的），填上就重新出现。`<meting-js>` 的 `type` 支持 `song` / `playlist` / `artist` / `album`，单曲就写 `type: song`。

MetingJS 这个版本默认调用 `https://api.i-meto.com/meting/api?server=<服务商>&type=<类型>&id=<号>`，域名确实写在 `Meting.min.js` 里，但那只是**默认值**——同一行是 `this.api = this.meta.api || window.meting_api || "https://api.i-meto.com/..."`，而 `api` 正是 `<meting-js>` 认的属性之一，所以换端点不用碰插件源码。主题模板（build-time 和 runtime 两份 `audioplayer.ejs`）因此多输出一行 `api="<%- theme.meting.api %>"`，值写在 `_config.yml`；这个字段留空时属性是 `api=""`，空串 falsy，会回落到 i-meto 默认，等于没改。

先看 i-meto 那份实测：这个端点**走本机代理会 403（Cloudflare 挡的，直连 200）**；元数据（标题/作者/封面/歌词）拿得很顺，但**音频地址是按曲目授权给的**——

| 检查 | 结果 |
| --- | --- |
| 网易云自己的 `music.163.com/api/song/detail/?id=448155` | `fee: 1`，即 VIP/付费曲 |
| `api.i-meto.com/...&type=url&id=448155` | `404`，空 body |
| 同一端点取热歌榜 3778678 的前几首做对照 | 海屿你 / 明知故犯 / 于是 → `200 audio/mpeg`；甲乙丙丁 / 我不难过 → `404` |
| headless Firefox 里 `meting-js.aplayer.audio` | `error` 是 `MediaError code 4: Failed to open media`，`networkState: 3`，面板时长显示 `00:00 / 00:00` |

也就是说端点是活的、配置是对的，448155（あなたがいた森 (TVサイズ) / 樹海）在 i-meto 上放不出声。换成同协议的 `https://api.injahow.cn/meting/?server=:server&type=:type&id=:id&r=:r` 之后能响——

| 检查 | i-meto | injahow |
| --- | --- | --- |
| 直连 / 走 7897 代理取元数据 | 200 / 403 | 200 / 200 |
| `type=url&id=448155` | `404` 空 body | `302` 到 `m702.music.126.net/...mp3`，带 Range 请求回 `206 audio/mpeg` |
| CORS | `Access-Control-Allow-Origin: *` | `*`，302 那一跳和最终音频都带 |
| headless Firefox 实测 | `MediaError 4` | `error: null`，`currentTime` 走到 4.0，面板显示 `00:05 / 00:30` |

但**只有 30 秒**：把那个 481115 字节的流存下来 `ffprobe` 是 `duration=30.000000`、`bit_rate=128297`，浏览器里 `aplayer.audio.duration` 同样是 30。`fee: 1` 的曲子网易云只发免费试听段，公共 meting 端点只是替客户端签了个 CDN 地址，绕不过授权——换端点改变的是"响不响"，不是"完整不完整"。要整首只有两条路：换任意 `fee: 0` 的曲目号（改 `meting.id` 一行），或者把音频文件自托管挂上去。

两个已知代价：injahow 是社区公益端点、没有可用性承诺，它哪天挂了面板就退回"封面歌词在、播放不响"，回退动作是删掉 `meting.api` 那行；另外它响应时间方差大，headless Firefox 里等 6 秒时 `meting-js.aplayer` 还没实例化、14 秒才稳，写验证脚本时 `--wait` 要给够。

### 换成 B 站收藏夹当歌单：数据拿得到，音频放不出

想把自己那个收藏夹（`fid=1190530554`，即 `https://www.bilibili.com/list/ml1190530554`）挂成歌单、只播音频。分三层，前两层没问题，第三层是死路：

| 层 | 实测 |
| --- | --- |
| 收藏夹元数据 | 匿名可读。`api.bilibili.com/x/v3/fav/folder/info?media_id=1190530554` 与 `x/v3/fav/resource/list?media_id=&pn=&ps=` 都回 `code:0`，全站 996 条，每条给 `bvid`/标题/时长/封面/UP 主。翻页就是 `pn` |
| 曲目直链 | `x/player/playurl?bvid=&cid=&fnval=16` 匿名可拿，DASH 里 `sound` 段的 `baseUrl` 就是纯音频流 |
| 让浏览器播这个流 | **不行**。同一个 `upos-sz-mirrorcos.bilivideo.com/...m4s` 地址：不带 Referer → 403；带 `Referer: https://takomitkm.github.io/` → 403；带 `Referer: https://www.bilibili.com/` → 206。UA 换桌面/安卓都一样。CDN 回 `Access-Control-Allow-Origin` 且跟着请求 Origin 走，所以卡的不是 CORS 是 Referer，而浏览器发媒体请求时的 Referer 由页面来源决定，网页脚本改不了（`<meta name="referrer">` 只能收窄、不能伪造成 bilibili） |

meting 端点这一侧也帮不上：`api.i-meto.com` 对 `server=bilibili` 直接回"server 参数不合法"，`api.injahow.cn` 回 `{"error":"unknown type"}`，两家都没有 bilibili 服务商。`Meting.min.js` 里的 `server` 字段是原样拼进请求 URL 的，客户端没有白名单（源码里 `netease`/`tencent`/`xiami` 那几个字符串只出现在 `_parse_link`，也就是"粘链接解析"那条分支），所以插件这边改不出花来。

结论：静态站（GitHub Pages 只有静态托管）做不到，必须有个服务端去带 `Referer: https://www.bilibili.com/` 转发音频流——Workers / Deno Deploy / 自己那台 Debian 都行，代价是这条链路变成"依赖我自己的服务器"，服务器挂了播放器就哑。唯一不需要中继的路子是官方 iframe：`player.bilibili.com/player.html?bvid=&page=1` 实测 200、无 `X-Frame-Options`、`Access-Control-Allow-Origin: *`，能嵌，但那是整块视频播放器，出画面，APlayer 的进度条和歌词面板都用不上，等于把右下角那块面板换成一个 iframe。

## 访客能改的样式，和它们存在哪里

全站一共五组"访问者可以自己调"的东西，全部落在 `localStorage`，读写都在 `source/asset/js/common/config.js`：

| 面板 | 项 | 存储 |
| --- | --- | --- |
| `.p-skin` 皮肤 | `default`（黑白） / `gray`（整站转灰） / `colorful`（图标彩虹色） | `config.skin` |
| `.p-settings` 设置 | `langshift` 中英切换、`night` 夜间模式、`transfigure` 看板娘半透明、`lyride` 隐藏播放器歌词、`autoplay` 自动播放 | `config.<key>` |
| `.p-xcanvas`（那个 `fas fa-video` 按钮） | 背景动画开/关，关掉时一并藏看板娘 | 独立键 `noCanvas`，不在 config 对象里 |
| 左抽屉、右侧栏的折叠按钮 | 收起 / 展开 | `config.closeDrawer`、`config.closeAside` |
| `.p-translater-bar` 划词翻译 | 目标语言 中 / 英 / 日 | `config.translater`，这次新加的 |

其中皮肤、`transfigure`、`lyride`、`autoplay` 和划词翻译是桌面端专属：`settings.styl` 在 `@media (max-width: $app_mobile_width)` 里把后三个设置项 `display none`，`translater.styl` 让整条划词条在移动端不显示，`applyConfig()` 里包皮肤那段走 `util.runOnDesktop`。

### 记忆规则：访客选过的优先，没选过的才用默认

`applyConfig()` 在页面所有部件加载完之后跑，把 `config.get(...)` 的值逐个 `set` 回界面。原来这里有个坑：`skin.set()` 和 `settings.set()` 会回头调用自己注册的 `onclick` 监听，而监听体的最后一句就是 `config.set(...)`——于是**第一次访问、还没等人动手，整套默认值就被当成"访客的选择"写进了 localStorage**。任何"访客有没有选过"的判断都会因此失真，所以 `skin.js` / `settings.js` 的 `set()` 多了一个 `byUser` 参数，只有点击路径传 `true`，监听里改成 `byUser && config.set(...)`。

光堵这一层还不够：`config.set()` 写的是整个合并后的对象，访客只要改过任意一项（比如只选了翻译语言），`skin` 的默认值也会被一起存进去。所以"选没选过"不能看 `config` 这个键——`config.js` 里另开一个 `configChosen` 数组，只在真正发生写入时记下键名，`config.has(key)` 读它。

自动切 colorful 就建立在这条判断上：加载完成时如果 `config.has('skin')` 为假，3 秒后执行 `skin.set('colorful')`；这 3 秒里访客自己点了皮肤，`skinPicked` 标记会让这次定时器作废。自动切换本身**不写存储**，所以下次来还是"3 秒后变彩色"，除非他自己选过。

| 场景 | 实测 |
| --- | --- |
| 全新配置，加载完等 7 秒 | 根元素 class `lyride colorful`，71 个图标被着色 |
| 同上，看存储 | `config` 和 `configChosen` 都是 `null`，说明没被写过 |
| 手动点"灰度"后重开，等 8 秒 | `lyride gray`，色块高亮在灰度，着色图标 0 个，没有被自动改回彩色 |
| 手动点"默认"后重开，等 9 秒 | `lyride`，仍然是默认皮肤 |
| 旧遗留：`config` 里有 `skin` 但没有 `configChosen` | 照样 3 秒变彩色 |

### GitHub 图标不参与彩虹色

`colorful` 皮肤做的事是 `colorIcons.run()`：把所有 `i.fas / i.fab / i.far` 按 `color_1…color_5` 轮转上色，`color_3` 就是那个 `#00CC99`。`skin.js` 里加了一张排除表 `exclude: 'i.fa-github'`，命中的直接跳过，连 `data-colored` 标记都不打。实测 colorful 皮肤下联系方式里的 GitHub 图标 `class` 仍是 `fab fa-github fa-fw`，`getComputedStyle().color` 是 `rgb(0, 0, 0)`。

## 划词翻译换成谷歌公共接口

原来是 `util.baiduTranslate`，走百度翻译开放平台的 JSONP，要 `appid` + `appkey` 签名（密钥用 `decodePass` 从 `api/site.json` 的 `baidu_translate.pass/pointer` 还原）。**这套凭据从来没填过**——`site.json` 里那两个字段是空串，所以划词翻译此前一直是"点了没结果"。

现在换成 `util.googleTranslate`，用 Chrome 内置翻译自己在调的那个免密钥接口 `https://clients5.google.com/translate_a/t?client=dict-chrome-ex&sl=auto&tl=<目标>&q=<文本>`，返回 `[["译文","识别到的语种"]]`，逐段取第 0 个拼起来。界面里的 `zh/en/jp` 映射成谷歌的 `zh-CN/en/ja`。

浮动条上那个标题写明是谁在翻：`asset/lang/zh-cn.yml` 的 `translater.to` 改成"划词翻译（谷歌）"、`en.yml` 改成 `HIGHLIGHT 'N TRANSLATE (Google)`。这两个 key 由 `translater.ejs` 里的 `<span class="p-translater-bar-to" data-lang="translater.to">` 在运行时填（build-time 和 runtime 两份模板同一个标记），所以只改 yml 就够，不用碰模板和 JS；`hexo generate` 会编译成 `public/asset/lang/{zh-cn,en}.json`，实测 480px 移动端下条宽 260px、没有横向溢出。

| 检查 | 结果 |
| --- | --- |
| `translate.googleapis.com/translate_a/single?client=gtx` | 本机代理出口 `429 Sorry...`，换 `translate.google.com` 同端点也 429，弃用 |
| `clients5.google.com/translate_a/t?client=dict-chrome-ex` | `200`，`Access-Control-Allow-Origin: *`，`hello world`→`你好世界`、`日本語`→`Japanese` |
| 同一端点不走代理直连 | 8 秒无响应，大陆网络到不了 Google |
| headless Firefox 实测 | 选中"日本語"点 EN → 结果框出 `RESULT / 翻译结果：Japanese`，面板加 `.active`；点中间那块"划词翻译"标签 → 用上次记住的 EN 再翻一次 |

三条要记着的：

1. **免密钥不等于免依赖**。谷歌这套接口没有 SLA 也没有配额承诺，`translate.googleapis.com` 那条对数据中心出口 IP 直接 429，`clients5` 只是另一条暂时能用的。
2. **大陆访客不开代理就用不了**，这是网络事实不是代码问题（直连 8 秒无响应）。失败时结果框给 `TRANSLATE FAILED / 翻译失败：…`，并有 8 秒 `AbortController` 超时兜底，不会让顶部转环一直转。
3. 译文**先转义再进 `innerHTML`**（`escapeHtml`），机翻结果里带尖括号也不会被当标签解析。

顺带清掉的依赖：`plugin/md5.min.js` 只被百度签名用到，`util.js` 里 `import fetch`（那个 JSONP 装载器）也只有它在用，两个引用都删了；`md5.min.js` 文件本身留在 `plugin/` 里没动，现在没人引用。

那个文件是什么：一份 MD5 的实现，MD5 是把任意长度输入压成 128 bit（写成 32 位十六进制）的摘要算法，这里被打包成 ES module（`export default o=>{...}`，3478 字节）。主题用它算百度翻译开放平台的请求签名 `sign = md5(appid + 原文 + salt + appkey)`——那个接口要求把签名放在 query 里，密钥不能直接发出去，所以必须有本地 MD5。换掉百度之后整条签名链没了，全仓库（排除 `public/`）对它的引用数是 0，只剩文件本身和一个 `asset/js/plugin/` 目录项。留着不影响构建（没人 `import` 就不会被 `hexo-generator` 之外的任何路径打进去，但它是主题的 `source/asset`，所以仍会原样复制到 `public/`，约 3.4KB）。

## 部署链路

`git push` 之后由仓库里的 `deploy` workflow 构建并发到 Pages，不需要任何个人访问令牌，也不需要把本地 `public/` 传上去。本地推送走代理：`git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push origin HEAD`。

PWA 这块：正文和列表都是运行时从 `/api/*.json` 取的，而 `sw-toolbox` 在 activate 时会清掉运行时缓存，所以页面 HTML、`/api/site|posts|tags|categories|search.json`、每篇的 `/api/posts/<abbrlink>.json`、每个 `/api/pages/<name>.json`、以及 `/asset/part/*.html` 必须走 precache 才能在离线时打开——这些列表写在 `scripts/renderer/$template.js` 里，加新页面时构建会自动带上。文章的固定链接是 `/posts/:abbrlink/`，只靠 front-matter 里的 `abbrlink`，所以**改 md 文件名和标题不会改 URL**。

## 怎么验的

截图核对用 `_tools/ffshot.mjs`：WebDriver BiDi 直连一个 headless Firefox，参数 `--url --out --profile --wait --size --eval --navwait --ua --proxy`。三个非默认项是补的：`--navwait none` 用于"页面里挂着流媒体 iframe 时 `complete` 永远不触发"的情况，`--ua` 通过 `general.useragent.override` 首选项改 UA，`--proxy` 给 BiDi 会话设 `network.proxy.*`（headless Firefox 不吃系统代理，测谷歌必须带）。退出前改成先调 `browser.close` 再 kill：只 kill 的话 `localStorage` 来不及落盘，跨启动的记忆测试会全假；即便如此，写入之后仍要在 eval 里 `await` 几秒等它 flush。样式和页内脚本改完要 `hexo clean && hexo generate` 才会落到 `public/`，光改文件不看构建产物等于没验。这次给 `.p-hitokoto-from` 加 `z-index` 时增量 `hexo generate` 只重写了 17 个文件、连 `public/asset/css/style.css` 的时间戳都没动，新规则完全没进去，`clean` 之后才出现——别信增量构建。

"这块底色是不是连续的"不能靠肉眼看缩略图：用 `--eval` 取 `getBoundingClientRect()` 量盒宽，再把截图按 4 倍 NEAREST 放大、用 PIL 沿某一行逐列读亮度，看框内有没有哪一列掉回框外图片的亮度——这次就是这样才量出旧实现名字和 `」-` 之间 6.667px 没涂。另一个坑：eval 里 `classList.add('night')` 之后立刻读 `getComputedStyle` 会拿到换肤前的颜色，哪怕中间 `await` 了两帧 rAF 也一样，得再 `setTimeout` 400ms 让主题的 CSS 变量落地，否则"夜间底色不对"是假的。

- 评论：主题只支持 Valine，需要 LeanCloud 凭据，而且主题把 appid/appkey 编码成 `pass + pointer` 两段存进 part 文件，不是填一行就完事的。要开评论再说。
